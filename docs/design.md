## 节点大小的解释

原文给出的结构在目标 64 位 ABI 上占 32 字节，已用静态断言检查结构头处于 32–512 字节范围。`dataSize` 按原文表示 `data` 指向的内容大小。基准程序覆盖 32–512 字节的数据；API 另外支持 1–31 字节，便于完整测试短数据比较。

一次分配占 `sizeof(LinkData) + dataSize` 字节，因此当数据为 512 字节时，头与数据合计为 544 字节（不包含 malloc 管理开销）。这区分了结构体大小、数据大小和分配大小；没有把三个概念混为一谈。若课程要求“头加数据总共最多 512 字节”，在 64 位环境将 `--size` 设为不超过 480 即可。

## 算法与内存

头节点不是哨兵，包含真实数据。尾插时间 O(1)，单次搜索最坏 O(n)，创建和释放链表 O(n)。多个相同数据节点中，返回遍历顺序的第一个。分配失败时既有链表仍有效；调用者应检查 InitLink 返回值或使用 AppendNodeChecked。

节点头和内容在一个内存块中，但不同节点仍分别分配；不能假设所有节点连续，也不把数组随机索引作为搜索捷径。普通版本和优化版本共享这种布局，所以对照实验主要评估前缀比较策略，不能将差异全部归因于内存布局。

没有宣称某个策略在所有处理器上“最快”。libc 的 memcmp 可能已经使用 SIMD，前缀高度相同或链表很短时，手动过滤也可能没有收益。共享前缀测试将唯一编号放在数据尾部，避免只挑有利样本。

## 大规模使用

头指针数组需要约 `8 × 链表条数` 字节，节点最低成本约为 `节点总数 × (32 + 数据长度)` 字节，再加分配器和查询缓冲区开销。默认每条链表 4096 个节点，仅是方便快速运行的参数。

例如 100 万条单节点、32 字节数据链表，仅头指针和节点内容约 72 MB；1000 万条相同链表约 720 MB，实际更多。100 万条链表各含 10000 节点则达到 100 亿节点，仅上述最小节点内容约 640 GB。程序不会承诺在普通电脑上同时容纳这些极端参数。

测试确实覆盖了每条 10000 节点及 1000 条独立链表；百万、千万条链表未作为已完成实测。程序检查参数乘法溢出，发现分配失败后释放已分配资源，但 Linux 内存过量承诺环境仍可能由系统 OOM 终止进程。

## 测量边界

1. 建立全部链表并生成查询，不启用硬件计数。
2. 执行预热查询，验证校验和。
3. 独立计时一遍搜索。
4. 分别打开指令/周期组、L1D 读访问/读未命中组、L1D 写访问组；每组重复预热并测量同一批查询。
5. 关闭组，读取并按事件 ID 对应计数；测量结束后再打印。
6. 多次试验交替两种算法的测量顺序，减少固定先后顺序的影响。

测量范围含查询循环、函数调用、读取返回节点编号、累加校验和及少量启停边界开销；不包含建链、随机数生成或 printf。没有扣除假设的常数开销，极短搜索应增加查询数。

跨组数值来自不同轮次，缓存、调度和频率变化仍会引入误差。读访问与读未命中同步分组，以使读命中率更合理。报告启用和实际运行时间，便于识别复用；少量运行时间的缩放结果可能不稳定。程序不把超范围命中率钳制成看似合理的 0% 或 100%。

## 结果判读

先检查 `verified=yes` 和 `hardware_metrics`，再比较同一组参数下两种算法多次结果。优先比较中位耗时、每次搜索指令数和周期数，并关注波动。小链表全部留在缓存中时，L1 命中率可能很高；这不能外推到百万条大型链表。

真实数据以实验日志为准。模拟计数器测试用于覆盖失败路径和数据解析，不是硬件性能测量。
